## Обзор

Сервис принимает от пользователя список URL, проверяет их доступность методом `HEAD`, сохраняет результаты на диск и присваивает уникальный идентификатор (`links_num`). По этому идентификатору позже можно запросить PDF-отчёт, содержащий статусы ресурсов.

Сервис не требует внешних сервисов (БД, nginx etc). Все данные хранятся локально в файле `bbolt`.

## Функциональность

- Проверка доступности URL (поддержка `http` и `https`, автоматическое добавление схемы при её отсутствии)
- Присвоение каждому запросу уникального 64-битного идентификатора (`links_num`)
- Хранение результатов на файловой системе через `bbolt` (key-value store)
- Генерация PDF-отчёта по списку идентификаторов
- Graceful shutdown с сохранением всех данных на диск
- Поддержка конкурентной проверки URL
- Восстановление состояния после перезапуска

## API

### POST /api/check-links

Принимает JSON с массивом URL:

```json
{"links": ["google.com", "yandex.ru"]}
```

Возвращает статусы и идентификатор:

```json
{
  "links": {
    "google.com": "available",
    "yandex.ru": "not available"
  },
  "links_num": 1234567890123456789
}
```

### POST /api/get-report

Принимает JSON со списком идентификаторов:

```json
{"links_list": [1234567890123456789, 9876543210987654321]}
```

Возвращает PDF-файл (`Content-Type: application/pdf`).

### GET /ping

Health-check эндпоинт. Возвращает `200 OK` с телом `"pong"`.

## Запуск

### Требования

- Go 1.24+
- Доступ к интернету (для проверки URL)

### Сборка и запуск

```bash

# Запуск с сминимальной настройками
SERVER_ADDR=:8080 BBOLT_DATA_FILE=./data/my.db ./bin/app
```

## Архитектурные практики

Проект реализован в соответствии с принципами **чистой архитектуры** и **инверсии зависимостей**:

- **Разделение ответственности**: каждый компонент (`api`, `service`, `checker`, `storage`, `report`, `server`) выполняет строго свою задачу.
- **Зависимости через интерфейсы**: высокоуровневые компоненты зависят от абстракций, а не от конкретных реализаций.
- **Состояние изолировано**: все данные проходят через `storage`, который инкапсулирует работу с диском.
- **Конфигурация централизована**: все параметры задаются через `config.Config`, загружаемый из переменных окружения.
- **Грейсфул шатдаун**: при получении `SIGINT/SIGTERM` сервер перестаёт принимать новые запросы, завершает активные и гарантирует сброс данных на диск.

Подробно см. [ARCHITECTURE.md](./docs/ARCHITECTURE.md)

## Особенности реализации

- **Идентификаторы (`links_num`)**: генерируются как случайные 64-битные числа с проверкой на коллизии. Это исключает утечку информации о количестве запросов и упрощает масштабирование.
- **Хранилище**: используется библиотека `bbolt` - надёжный, конкурентно-безопасный key-value store на основе B+ деревьев. Все операции записи синхронизируются с диском при завершении работы.
- **Проверка URL**: выполняется конкурентно. Поддерживается автоматическое добавление схемы (`http://`, `https://`) и перебор схем при отсутствии явной.
- **PDF-генерация**: реализована через `gofpdf`. Отчёт содержит заголовок, сводную статистику и таблицу с деталями по каждому URL.
- **Обработка ошибок**: все компоненты возвращают ошибки через стандартный механизм Go. Критические ошибки логируются, клиенту возвращается `500 Internal Server Error`.

## Восстановление после перезапуска

Сервис может быть остановлен в любой момент. При *graceful shutdown* все завершённые задачи гарантированно сохраняются на диск. При аварийном завершении возможна потеря данных, не успевших сброситься на диск, но целостность уже сохранённых записей обеспечивается `bbolt`.

После перезапуска сервис восстанавливает доступ к ранее сохранённым результатам - запросы к `/api/get-report` с ранее выданными `links_num` работают корректно.
